## Ответы на теоретические вопросы:

**E. Почему `_rev` не является полноценной историей версий?**
`_rev` — это маркер ревизии, используемый для оптимистической блокировки (MVCC) и предотвращения конфликтов при одновременной записи. При сжатии базы (компактификации) старые ревизии удаляются, остаются только метаданные. Для хранения полной истории изменений необходимо создавать отдельные архивные документы.

**F. Схема хранения результатов AI-сервиса в CouchDB, PostgreSQL JSONB и Key-Value:**
* **CouchDB:** Идеально для offline-first приложений и распределенной синхронизации. Хранит документ целиком.
* **PostgreSQL JSONB:** Идеален, если данные AI-сервиса нужно связывать с реляционными данными (пользователи, биллинг) через `JOIN` и ACID-транзакции.
* **Key-Value (Redis):** Идеально для кэширования результатов по ключу `request_id`. Мгновенный доступ, но нет сложного поиска по полям.

**G. Какие поля нельзя сохранять без необходимости?**
Персональные данные (PII): ФИО, номера телефонов, паспортные данные, `access_token`, пароли и полный текст запросов, если в них есть конфиденциальная информация (в соответствии с 152-ФЗ / GDPR). Необходимо применять минимизацию данных и политики retention.
